# 제품 명세 변경

요구사항: $ARGUMENTS

이 단계에서는 `docs/PRODUCT_SPEC.md`만 수정한다. 코드, 테스트, 설정은 건드리지 않는다.

1. `docs/PRODUCT_SPEC.md`와 `AGENTS.md`를 읽는다. 명세가 없으면 `docs/PRODUCT_SPEC_TEMPLATE.md`를 복사해 시작한다
   (앱 이름은 `app/layout.tsx`의 metadata `title`에서, 배포는 `.vercel/`이 있거나 README에 Vercel 배포가 적혀 있으면 `Vercel`, 아니면 미결 질문으로).
2. 관련 코드를 읽어 현재 동작을 파악한다.
3. 명세 수정
   - 사람이 쓴 문장을 "원본 요구사항" 끝에 날짜와 함께 그대로 덧붙인다.
   - 새 기능은 다음 번호 `F-n`으로 추가하고 `기능 상태: 대기`. 기존 기능의 동작이 바뀌면 그 기능의 수용 기준과 테스트 계획을 고치고 `기능 상태: 대기`로 되돌린다.
   - 이미 구현된 기능 번호와 수용 기준 번호는 재사용하지 않는다(지운 기준은 지우고 번호는 비워 둔다).
   - 수용 기준은 테스트로 판정할 수 있게 쓰고, 모두 테스트 계획 표에 넣는다.
   - 외부 서비스, 로그인, DB, 비밀 값, 새 npm 패키지가 필요하면 이유를 적고 미결 질문에 확인을 요청한다.
   - API가 바뀌면 `## API` 표를, DB 테이블이 바뀌면 `## 데이터 저장`을 고친다. 기존 데이터를 지우거나 바꾸는 변경은 `## 위험 요소`에도 적는다.
   - `서버: 없음`인 프로젝트에 서버 기능이 필요해지면 `서버: 있음`으로 바꾸고, 서버 파일(WNAS 템플릿의 `lib/db`, `drizzle.config.ts` 등)을 다시 추가해야 한다는 점을 미결 질문에 적는다.
   - 모호한 점은 추측하지 말고 미결 질문에 적는다.
   - 맨 위 `- 상태:`를 `초안`으로 바꾸고 변경 이력에 오늘 날짜와 내용을 한 줄 추가한다.
   - **상태를 `승인`으로 바꾸지 않는다** (사람이 명시적으로 "승인"이라고 지시한 경우에만).
4. `scripts/check-spec.sh --draft docs/PRODUCT_SPEC.md`가 PASS할 때까지 고친다.
5. 짧게 보고: 바뀐 기능/수용 기준, 미결 질문, 다음 단계(검토 후 상태를 승인으로 → `/implement F-n`).
