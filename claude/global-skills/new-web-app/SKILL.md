# 새 웹앱 제품 명세 작성

요구사항: $ARGUMENTS

이 단계의 결과물은 **명세 초안 하나뿐**이다. 프로젝트 생성, 코드 작성, 템플릿 저장소 수정은 하지 않는다.

## 1. 템플릿 찾기

```bash
T="$(cd "$(dirname "$(readlink -f ~/.local/bin/new-web-app)")/.." && pwd)"
```

- `~/.local/bin/new-web-app`이 없으면 멈추고, WNAS README 5절의 설치 방법을 안내한다.
- `$T/docs/PRODUCT_SPEC_TEMPLATE.md`(형식)와 `$T/AGENTS.md`(사람 승인이 필요한 항목)를 읽는다.

## 2. 요구사항이 비어 있거나 한 단어뿐이면

명세를 쓰지 말고 무엇을 하는 웹앱인지 한두 문장을 요청한다.

## 3. 명세 작성

- 앱 이름: 영문 PascalCase(영문자/숫자만). 프로젝트 폴더는 kebab-case(`MyApp` → `~/my-app`)다. `~/app-specs/<이름>`이나 그 폴더가 이미 있으면 다른 이름을 고른다.
- 배포: 기본 `Vercel`. 사람이 배포하지 않겠다고 했으면 `없음`.
- 원본 요구사항: 사람이 쓴 문장을 **고치지 않고** 그대로 인용한다.
- 기능은 작게 나누고(`F-1`, `F-2` …), 처음 버전에 꼭 필요한 것만 넣는다. 나머지는 "범위 밖"에 적는다.
- 수용 기준은 테스트로 판정할 수 있게 쓴다: 화면에 보이는 정확한 문자열, 버튼 이름, URL, 경계값(0, 빈 목록, 최대값), 오류·로딩 상태, 모바일 화면.
- 테스트 계획 표의 모든 수용 기준에 테스트 방법(단위 테스트 / 컴포넌트 테스트 / E2E)과 증거(`NN-상태-설명` 스크린샷 이름 또는 테스트 로그)를 적는다.
- 로그인, DB, 외부 API, 결제, 분석 도구, 비밀 값(환경 변수)은 꼭 필요할 때만 넣고 이유를 적는다. 넣었다면 미결 질문에 확인을 요청한다(서비스 선택, 비용, 개인정보).
- **모호한 점은 추측해서 채우지 않는다.** 미결 질문에 적는다. 합리적 기본값을 제안할 때는 "가정: X로 하겠습니다. 맞나요?" 형식으로 질문에 넣는다.
- 상태는 `초안`. **상태를 `승인`으로 바꾸지 않는다** (사람이 명시적으로 "승인"이라고 지시한 경우에만).
- 변경 이력에 오늘 날짜로 "초안 작성". 검증 결과는 "- 아직 없음".

`~/app-specs/<이름>/PRODUCT_SPEC.md`에 저장한다.

## 4. 형식 검사

```bash
"$T/scripts/check-spec.sh" --draft ~/app-specs/<이름>/PRODUCT_SPEC.md
```

PASS가 나올 때까지 명세를 고친다. 검사를 실행하지 못했으면 그렇다고 보고한다.

## 5. 보고 (짧게)

- 명세 경로
- 기능 목록 (기능마다 한 줄)
- 미결 질문 목록
- 다음 단계: 명세를 읽고 고친 뒤 `- 상태: 초안`을 `- 상태: 승인`으로 바꾸고 미결 질문을 `- 없음`으로 정리 → `new-web-app --spec ~/app-specs/<이름>/PRODUCT_SPEC.md`

## 이후 대화에서 명세를 고칠 때

사람이 수정이나 답변을 주면 본문에 반영하고, 답한 질문은 지우고, 변경 이력에 한 줄 추가한 뒤 다시 `--draft` 검사를 한다. 상태는 초안으로 둔다.
